一、交接目标

交给另一位 agent 并行完成。

该任务与当前主会话负责的 build/compile_app、HAP signing、developtools_packing_tool、
Telephony/Contacts HAP Action 不重叠。接手者不得修改 build 仓，只能使用 build 输出和 Ninja
图进行只读定位；找到最早 dirty 的具体模块后，应转到该模块所属的独立源码仓建立修复。

优先选择源码位于独立仓库的模块。已有记录显示 Window Manager 和 Device Attest 相关动态库或
可执行文件曾在第二轮构建中重新链接，可先从这两类候选开始，但必须用本轮 Ninja 证据确认，

五、任务目标

从 phone_install_modules 的第二轮 dirty 链中找到最早发生无效重建的具体 .so 或可执行文件，
确认其所属独立源码仓，并在该组件仓内解决根因。

完整因果链必须达到：

具体源文件/生成文件/depfile/命令变化
  -> 具体链接目标重复执行
  -> 该二进制成为 phone_install_modules 输入
  -> phone_install_modules 被调度

不能只报告 phone_install_modules is dirty，也不能只报告某个 .so is dirty；必须继续追到最早
没有更早 dirty 解释的节点。

六、第一阶段：只读定位 phone_install_modules

1. 查询 GN target：

prebuilts/build-tools/linux-x86/bin/gn desc \
  out/rk3568 \
  //build/ohos/packages:phone_install_modules

prebuilts/build-tools/linux-x86/bin/gn desc \
  out/rk3568 \
  //build/ohos/packages:phone_install_modules outputs

prebuilts/build-tools/linux-x86/bin/gn desc \
  out/rk3568 \
  //build/ohos/packages:phone_install_modules inputs

prebuilts/build-tools/linux-x86/bin/gn desc \
  out/rk3568 \
  //build/ohos/packages:phone_install_modules deps --tree \
  > "$LOG_DIR/phone_install_modules_deps.txt"

2. 目标级 Ninja dry-run：

先以 gn desc 或 ninja -t query 确认准确输出路径，不要凭记忆写路径。然后执行：

prebuilts/build-tools/linux-x86/bin/ninja \
  -w dupbuild=warn \
  -C out/rk3568 \
  -n -d explain \
  '<phone_install_modules 的准确输出>' \
  > "$LOG_DIR/phone_install_modules_explain.log" 2>&1

3. 提取候选二进制：

grep -n -E \
  'dirty|missing|\.z\.so|\.so|/bin/|executable' \
  "$LOG_DIR/phone_install_modules_explain.log" \
  | head -500 \
  > "$LOG_DIR/phone_install_modules_candidates.txt"

4. 对第一个直接 dirty 的具体二进制执行：

prebuilts/build-tools/linux-x86/bin/ninja \
  -C out/rk3568 \
  -t query \
  '<具体二进制输出>' \
  > "$LOG_DIR/first_binary_query.txt"

prebuilts/build-tools/linux-x86/bin/ninja \
  -w dupbuild=warn \
  -C out/rk3568 \
  -n -d explain \
  '<具体二进制输出>' \
  > "$LOG_DIR/first_binary_explain.log" 2>&1

继续逐层查询，直到找到最早 dirty 输入。

七、第二阶段：区分 dirty 类型

对最早候选节点记录：

- 输出路径；
- 所属 GN label；
- 所属源码仓；
- 直接 inputs；
- depfile/rspfile；
- .ninja_log 中两轮命令哈希或执行记录；
- 文件 mtime、size、SHA-256；
- 内容是否真实变化；
- 命令行、输入顺序、生成文件顺序是否变化。

建议命令：

stat -c '%n|%Y|%y|%s' '<输出文件>'
sha256sum '<输出文件>'

prebuilts/build-tools/linux-x86/bin/ninja \
  -C out/rk3568 \
  -t commands \
  '<具体二进制输出>' \
  > "$LOG_DIR/first_binary_commands.txt"

如果有此前保存的两轮 .ninja_log，应比较两轮记录，不要启动完整构建来制造新数据，除非操作者
明确授权。

将根因分类为以下一种或多种：

1. 生成文件内容变化；
2. 内容不变但 mtime 被刷新；
3. depfile/rspfile 不稳定；
4. 命令行或输入顺序变化；
5. 链接产物本身不可重复；
6. 声明输出缺失；
7. 输入真实变化，属于必要重建。

若确认是第 7 类，不得“修复”为跳过构建，应继续找到造成真实输入变化的更早节点。

八、第三阶段：转入独立组件仓

确定组件仓后：

1. 记录仓库路径、当前分支、HEAD 和工作树；
2. 若工作树不干净，停止修改并汇报；
3. 从该整仓快照的组件 HEAD 建立验证分支；
4. 正式 PR 分支应另从该组件最新上游建立，并单独处理跨仓兼容性；
5. 只修改最早根因所在组件，不修改 build 仓；
6. 一个提交只修一个根因；
7. 先进行组件级或函数级测试，再给出完整构建验证命令。

候选独立仓只能作为起点，必须以 GN label 和 repo 信息确认：

- foundation/window/window_manager（如实际重复链接目标归属 Window Manager）；
- 对应 Device Attest 组件仓（必须通过 repo manifest 或 git remote 确认准确路径和仓名）；
- Ninja explain 指向的其他独立组件仓。

不要因为历史记录提到 Window Manager 或 Device Attest 就直接改它们。

十二、完成判定

只定位到 phone_install_modules 或某个 .so 不算完成。至少满足以下之一：

A. 已定位最早 dirty 根因，确认独立组件仓，并完成可审查补丁及轻量验证；

或

B. 已用完整证据证明该输入是必要重建，并继续定位到造成真实变化的更早独立组件节点；如果因
缺少两轮日志或 Ninja 图不可用而无法继续，应明确报告阻塞信息，不得猜测修复。

本文优先级高于旧聊天中的临时结论。实际仓库状态若与本文不一致，应先停止修改并报告差异。

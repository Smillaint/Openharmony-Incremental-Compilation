## 2. 处理原则

- OpenHarmony 根目录由多个独立 Git 仓库组成，没有在源码根目录重新执行 `git init`。
- 在涉及修改的各子仓库中创建统一分支 `action_incremental_fix_20260804`。
- 不覆盖、不提交原先存在的 `package-lock.json`、`node_modules` 等无关修改。
- `sane-airscan` 旧 ACTION 对源码目录产生的修改和 `.rej` 文件已保存到该仓库的 `stash@{0}`。
- 后续只有在操作者明确要求执行编译时，才允许通过 SSH 启动编译。普通分析、日志检查和代码修改不自动触发编译。

## 3. 根因分析

### 3.1 `gen_snapshot` 与 `ark_jsf`

`third_party/css-what` 将目录复制到 `obj/third_party/jsframework/runtime`，生成 `css_what_sources.stamp`。随后 `gen_snapshot` 又向同一个 `runtime` 目录写入文件，导致目录时间晚于 stamp，形成以下持续变脏链路：

```text
css_what_sources.stamp
  -> obj/third_party/jsframework/runtime
  -> gen_snapshot
  -> dist/strip.native.min.js
  -> ark_jsf
```

同时，JS 构建脚本会重复生成内容未变化的 `strip.native.min.js`，进一步造成时间戳变化。

修复方式：

- 保留共享 `runtime` 目录，不在每轮构建中删除并重新创建。
- 对内容未变化的 `strip.native.min.js` 恢复原时间戳。
- JS 构建完成后，将共享 `runtime` 目录时间稳定到对应 `css_what_sources.stamp`，消除目录自身触发下一轮 ACTION 的循环。

### 3.2 `airscan_action`

原 ACTION 直接修改 `third_party/sane-airscan` 源码目录。补丁重复应用时会留下源码修改和 `.rej` 文件，使源输入持续变化，破坏 Ninja 的增量判断。

修复方式：

- 将需要参与编译的 C 文件和头文件复制到生成目录。
- 只在生成目录应用补丁，源码目录保持不变。
- 编译目标改为使用生成目录中的 patched sources。
- 排除 OpenHarmony 当前不支持依赖的 Avahi、TIFF、WSD 后端实现文件。

### 3.3 其他生成脚本

本地修改方案还涉及 Python 生成脚本无条件重写输出的问题。远端补丁补充了以下处理：

- 仅在内容实际变化时重写 NOTICE、资源和一致性检查输出。
- 缓存的 NOTICE JSON 无效或为空时可以重新生成。
- IDL 可选输出不存在时跳过时间戳稳定操作，避免 `FileNotFoundError`。
- 为生成动作补充明确输入，使 Ninja 能正确判断依赖变化。
